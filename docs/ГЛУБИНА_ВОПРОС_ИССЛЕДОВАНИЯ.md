# Исследовательский вопрос: контракт `ResearchQuestion → X → DerivedQuestion`

**Статус:** контракт, до кода и до объявления пробы. Решения владельца по разбору
вариантов — в `docs/ГЛУБИНА_ЭКСПЕРИМЕНТ.md`, раздел 7. Задача этого документа одна:
определить связку так, чтобы X не был заранее типизирован — ни как остаток, ни как условие,
ни как сумма, ни как взгляд вперёд. Если контракт получается чистым, объявляется
следующая диагностическая проба. Если нет — сначала исправляется контракт.

---

## 0. Определение

> **Исследовательский вопрос** — вопрос, целью которого является получение промежуточного
> знания, необходимого или потенциально полезного для решения другого открытого вопроса.

```text
Question
  ├── решающий вопрос        найти ответ на цель
  └── исследовательский вопрос
            ↓
         наблюдение X
            ↓
      производный вопрос     решающий или снова исследовательский
            ↓
          ответ
            ↓
      пересборка родителя
```

Исследование становится частью рассуждения, а не отдельным инструментом. Глубина — цепочка
«вопрос → результат → новый вопрос → результат → …», а не только «задача → подзадача».

---

## 1. Объекты контракта

| Объект | Что это | Чего в нём нет |
|---|---|---|
| `Question` | открытый вопрос: входы, цель, domain (как `Problem` в D1) | вида вопроса |
| `ResearchQuestion` | родитель (открытый вопрос), **эксперимент** (программа), бюджет | вида эксперимента |
| `Observation` | значение, которое вернула программа эксперимента, одного из **видов значений** (раздел 2), и журнал того, что было вычислено и почём | смысловой метки («это остаток», «это условие») |
| `DerivedQuestion` | новый вопрос, построенный **программой вывода** из родителя и наблюдения; решающий или исследовательский | вида |
| `Rebuild` | **шаблон** на языке ответа: как из наблюдения и ответов производных вопросов собрать кандидата для родителя | смысла шаблона |
| `ResearchRecord` | история: родитель, программа эксперимента, цена по статьям, наблюдение, производные вопросы, их ответы, кандидат, вердикт родителя до и после, использован ли X в ответе родителя, а также — только прибором — прав ли ответ на мире | **поля «ценность»** |

**Ценность не хранится.** Она вычисляется потом из истории — например, как снижение цены
подзадачи или как выигрыш родителя в битах. Какую величину считать хорошим исследованием,
решает D2 по записям, а не контракт. Иначе человек снова заранее определил бы, что считать
хорошим исследованием.

Тройка «эксперимент, вывод, пересборка» — это **план исследования**. Все три части — данные:
программы и шаблоны, которые интерпретатор исполняет, не зная, что они значат.

## 2. Язык экспериментов

Программа эксперимента — выражение над доступными объектами. Примитивы берутся только из
того, что вычислитель уже делает (тот же принцип, что у метаязыка P1).

**Виды значений** — не смысловые типы, а форма данных:

| Вид | Что это |
|---|---|
| P | программа на языке ответа (DSL) |
| V | вектор значений по точкам |
| M | маска точек |
| N | число |
| L | список значений одного вида |

**Доступные объекты:** входы, цель и domain родителя; словарь поиска (листья и условия);
при желании — журнал поиска родителя (луч, пул).

**Примитивы:**

| Группа | Примитивы | Откуда |
|---|---|---|
| вычисление | `eval(P, M) → V` | вычислитель |
| сравнение | `eq(V, V) → M`, `neq`, `and`, `or`, `not` над M, `count(M) → N` | вычислитель, P1 |
| арифметика по точкам | `add(V, V)`, `sub(V, V) → V`; `bool(M) → V` | вычислитель |
| мера | `bits(P, V, M) → N` — длина описания P как ответа на V при M; `distinct(V, M) → N`, `table_bits(V, M) → N` | `description` |
| поиск как проба | `search(V, M, b) → P` — плоский поиск с бюджетом b; тратит бюджет | поиск как есть |
| наследники | `successors(P, rules) → L[P]` | интерпретатор политики (P1b) |
| кандидаты | `candidates(s) → L[P]` — программы словаря до размера s | правки поиска |
| перебор | `argmin(L, λ)`, `argmax(L, λ)`, `take(k, L)`, `sort(L, λ)` | P1 |

**Программа вывода** `DerivedQuestion` — выражение того же языка, дающее новые (входы,
цель, domain). Входы можно расширить столбцом `eval(P)`: это «новый элемент», и контракт его
не запрещает.

**Шаблон пересборки** — выражение языка ответа с дырами: наблюдение-программа и ответы
производных вопросов.

**Чего нет среди примитивов:** остатка, покрытия, развилки, взгляда вперёд, нового
элемента, суммы, условия-развилки. Всё это — программы, записанные в каталоге как данные.

## 3. Проверка чистоты на бумаге: всё ли известное выражается без типов

| Что | Эксперимент (→ X) | Вывод производного вопроса | Пересборка |
|---|---|---|---|
| ветвь D1b «остаток» | `X = search(t, D, share)` | `(sub(t, eval(X, D)), D)` | `X + ?` |
| ветвь D1b «остаток-» | то же | `(sub(eval(X, D), t), D)` | `X − ?` |
| ветвь D1b «промахи и случаи» | то же | 1) `(t, and(D, neq(eval(X), t)))` → R′; 2) `(bool(eq(eval(X), t)), neq(eq(eval(X),t), eq(eval(R′),t)))` → C | `if(C, X, R′)` |
| A: «после X остаток проще» | `argmin(candidates(s), λx. bits(x, t, D) + bits(search(sub(t, eval(x)), D, b₀), …))` | как «остаток» | `X + ?` |
| A: «X точен на большей части точек» | `argmax(candidates(s), λx. count(eq(eval(x), t)))` | как «промахи и случаи» | `if(C, X, R′)` |
| A: «условие, после которого обе стороны проще» | `argmin(conditions, λc. bits(search(t, and(D, eval(c))), …) + bits(search(t, and(D, not(eval(c)))), …))` | две стороны: `(t, and(D, c))`, `(t, and(D, not c))` | `if(c, ?, ?)` |
| C: «где цель совпадает с листом» | `X = eq(eval(leaf), t)` — наблюдение-маска | `(t, and(D, not(X)))` | `if(?, leaf, ?)` |
| шаг P2-класса | `X = argmin(successors(s, A′), λy. bits(y, t, D))` для s из пула | любой из выводов выше | как у вывода |
| «новый элемент» (D3) | `X = search(…)` | входы ∪ {u = eval(X)} | подставить X вместо u |
| вопрос над вопросом | эксперимент, поставленный на производный вопрос | — | — |

Все известные случаи выражаются одним интерпретатором: вид значения плюс примитивы, без
смысловых типов. Три вопроса A, маски C, ветви D1b, шаг P2 и новый элемент — строки
каталога, а не ветви кода. Вопрос над вопросом — просто исследовательский вопрос,
поставленный на производный.

## 4. Где чистота неполная — честно

1. **Виды значений** P, V, M, N, L — выбор под мир discovery. Знание другой формы
   (отношение, инвариант, ограничение-неравенство) потребует нового вида. Контракт открыт,
   если язык расширяем, но сам вид значения MANA пока не изобретает.
2. **`candidates(s)`** — пространство кандидатов с параметром размера. По решению
   владельца — тот же словарь, что у плоского поиска, но размер s выбирает человек.
3. **Шаблоны пересборки** написаны на языке ответа, поэтому пересобрать можно только то,
   что язык ответа умеет выразить.
4. **Бюджет исследовательского вопроса** — сколько тратить — вне контракта. Это
   распределение (P2d, H3b), то есть D2. Фиксированное правило в пробе должно быть
   объявлено и не должно предопределять результат (урок D1b).
5. **Каталог первых экспериментов** (A, C, ветви D1b, шаг P2) пишет человек. Контракт
   чист, каталог — нет. Поэтому на пробе каталог — диагностический: все его строки
   равноправны, ни одна не считается заранее правильной.
6. **Мера в примитиве `bits`** несёт найденную симметрию двух значений (D0, 4.5).
   Программы, которым это важно, используют счёт точек (`count(eq(…))`). Это свойство меры,
   а не контракта.

Ни один из этих пунктов не вводит смыслового типа X. Все они — границы языка и каталога,
и их можно измерить.

---

## 5. D2 и D3 в этом контракте

- **D2 — политика над экспериментами.** Человек задаёт пространство: каталог планов
  исследования. MANA учится по `ResearchRecord`, какой план ставить и сколько в него
  вложить.
- **D3 — изобретение представления экспериментов.** MANA сама составляет новые программы
  эксперимента, вывода и пересборки на языке раздела 2 — планы, которых в каталоге не было.
  Это настоящий Н3: механизм внутреннего рассуждения порождает конструкции, которых мы не
  предусмотрели.

## 6. Следующий шаг — до объявления пробы

Проверку чистоты на бумаге стоит подтвердить исполнением. Это небольшой шаг, по образцу
D1a:

1. **Интерпретатор контракта** (объекты раздела 1 и язык раздела 2). Тест по исходнику:
   в нём нет ни одного имени вида вопроса — ни остатка, ни покрытия, ни развилки, ни
   взгляда.
2. **Каталог как данные.** Ветви D1b, три вопроса A, маски C и шаг P2 записываются
   программами.
3. **Тождество.** Ветви D1b через контракт дают ровно то же дерево, что
   `problems.solve` (D1b-A), на экземплярах лестницы — поле в поле, как D1a.

Только после этого — объявление диагностической пробы: каталог A/C как равноправные
кандидаты, R4 и R5 — главный объект, контроли S, C1 и миры вне лестницы, правило канала —
как в 1c.

## 7. Ворота контракта — обязательны перед любой пробой (решение владельца, 2026-09-15)

Реализация: интерпретатор — `mana/discovery/questions.py`, каталог планов как данные —
`mana/discovery/plans.py`. Четыре независимые проверки.

1. **Смысловая слепота интерпретатора.** Тест читает исходник: в нём нет ни одного названия
   вида вопроса. Русские основы (остат-, покрыт-, развилк-, промах-, случа-, «новый
   элемент») ищутся как подстроки, английские слова (remainder, residual, cover, split,
   look, misses, cases…) — как целые слова. В классах исполнения (`_Interpreter`, `_Scope`)
   нет проверок формы значения (`isinstance`, `type`). Интерпретатор не видит миров и
   лестницы.
2. **Каталог — данные.** Каждый план каталога проходит через один и тот же интерпретатор:
   ветви D1b, три вопроса A, маски C, шаг P2-класса. Если убрать план, его вопросы исчезают
   из дерева.
3. **Тождество D1b и нулевой случай.**
   - Тестом на малой задаче при долях 1, 1/2, 1/4.
   - В полном объёме — `scripts/run_questions_gate.py`:
     - **нулевой случай** — пустой каталог ровно равен плоскому поиску на 160
       экземплярах лестницы и контролей и 70 классических: все поля поиска, весь счёт в
       статье «поиск», один узел, ни одной записи;
     - **D1b через контракт** — ровно `problems.solve` (D1b) на 160 экземплярах при долях
       1, 1/2, 1/4, то есть на 480 сравнениях. Сравниваются ответ, все поля поиска корня,
       счёт по статьям, всё дерево (оператор, родитель, зависимости, бюджет, цена,
       программа, выбранный план, использованные узлы, дети) и использованная глубина.
4. **Композиционность.** Исследовательский вопрос ставится на вопрос, построенный из
   собственного наблюдения X (Q0 → X → Q1(X) → исследование Q1 → Y). Используется тот же
   класс узла и тот же путь исполнения. Использованная глубина — не меньше 3.

**Прогноз до прогона.** Все проверки проходят:
- нулевой случай — 230 из 230;
- D1b через контракт — 480 из 480, поле в поле.

**Правило ворот.** Любое расхождение означает, что контракт не чист: сначала исправляется
контракт, никакая проба до этого не объявляется.

Прогон тождества — 1 920 с. Все тесты проекта прошли (2 258).

**Прогноз сбылся целиком. Ворота пройдены.** Контракт `ResearchQuestion → X →
DerivedQuestion` исполняется интерпретатором, который не знает ни одного вида вопроса и не
смотрит на форму X. Три ветви D1b, записанные данными, дают ровно D1b — на деревьях до 315
узлов, узел в узел. Пустой каталог — ровно плоский поиск.

Можно объявлять следующую диагностическую пробу. Первая — двухуровневое исследование:
`Goal → X → Y`.
