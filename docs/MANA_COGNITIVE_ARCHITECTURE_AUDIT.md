# Аудит архитектуры MANA перед переходом к открытой когнитивной системе

**Версия на момент аудита:** 5.12.3 · 11 800 строк кода, 4 500 строк тестов, 35 модулей
**Статус набора тестов:** 389 passed, 8 skipped, 2 падения существовали до начала работ
**Дата:** 3 сентября 2026

Это фаза 0. Ничего не переписано. Документ фиксирует, что в системе есть на самом
деле, что только выглядит работающим, и где проходят настоящие границы — до того,
как поверх них что-то строить.

---

## 1. Текущая архитектура

Пакет `mana/` — 25 модулей, плюс 8 миксинов в `agent_parts/`, собираемых в один
класс `ManaAgent` (`mana/agent.py` — 39 строк, только композиция).

```
СЛОЙ РЕСУРСОВ
  brains.py        BrainPool — 14 мозгов в каталоге, выбор по задаче,
                   квоты, circuit breaker, консенсус, зондирование локальных
  tools.py         ToolRegistry — 11 инструментов, реальный путь диспетчеризации
  web.py           WebSearcher поверх ddgs с circuit breaker
  verifier.py      LocalVerifier — арифметика через AST + песочница подпроцессом

СЛОЙ ПАМЯТИ
  memory.py        MemoryManager — SQLite WAL, события, факты, FTS5
  graph_memory.py  GraphMemoryStore — дистилляция реплик, рёбра, обход графа
  knowledge.py     KnowledgeBase — legacy pickle-память + эмбеддинги
  experience.py    ExperienceDB — журнал исходов для отбора пайплайнов

СЛОЙ ИСПОЛНЕНИЯ  (agent_parts/)
  context.py       сборка промпта из памяти, графа, веба, знаний
  routing.py       local/web/mixed + обученный классификатор
  confidence.py    выбор архитектуры, оценка и калибровка уверенности
  execution.py     критик/repair, генерация тестов, adaptive-граф, _answer_core

СЛОЙ ИЗМЕНЕНИЯ
  pipeline.py      PipelineSpec (геном, 30 полей) + PipelineFactory
  benchmarking.py  измерение: бенчмарки routing/adaptive/control
  evolution.py     GA-цикл evolve_pipeline, ворота приёмки, self_improve
  code_evolution.py gated-патчинг собственного исходного кода

ГРАНИЦЫ
  paths.py         install/data/package roots, песочничный интерпретатор
  events.py        единый канал вывода (шина событий)
  config.py        Config — 150+ полей
```

### Что здесь важно для перестройки

Существующая система **уже разделена на слои правильно**. Ресурсы отделены от
исполнения, исполнение от изменения. Это не потребует ломки: когнитивный слой
ложится **над** исполнением и **под** эволюцией.

## 2. Жизненный цикл задачи

```
solve_task(task)                          core.py:solve_task
  ├─ проверка на неоднозначность          intent.py
  ├─ answer(task, spec)                   execution.py
  │    └─ _adaptive_answer_v41            execution.py — исполнитель графа
  │         ├─ _graph_for_task            какие узлы и в каком порядке
  │         └─ цикл по узлам:
  │              MEMORY   → _build_context (граф-память, знания)
  │              WEB      → web_search
  │              LLM      → _answer_core → _brain_strategy
  │                           single / consensus / decompose
  │              CRITIC   → _critic (на другом мозге, если есть)
  │              REPAIR   → на мозге-авторе
  │              SYNTHESIS→ llm_generate
  │              EXECUTE  → verify_answer / run_code
  │              EVALUATE → остановка по уверенности или бюджету
  ├─ запись в graph_memory                record_turn + maybe_rollup_episode
  └─ _record_route_outcome + _record_brain_outcome
```

**Это уже когнитивная программа.** `graph_nodes` — последовательность операторов,
`_adaptive_answer_v41` — её интерпретатор. Отличие от требуемого:
последовательность, а не граф; фиксированный словарь из 8 узлов; узлы не имеют
типов, предусловий и стоимости.

## 3. Цикл эволюции

```
self_improve()                            evolution.py:self_improve
  ├─ baseline: benchmark + holdout + routing holdout
  ├─ evolve_pipeline(budget)
  │    ├─ _initial_population             из ExperienceDB + мутации чемпиона
  │    ├─ SCREEN: 4 задачи на кандидата   быстрый отсев
  │    ├─ FULL: train + generalization    для выживших
  │    ├─ _compare_to_champion            парная статистика, z-оценка
  │    └─ _causal_probe                   по одному изменённому полю (диагностика)
  ├─ _precheck_diagnostics                ворота: fitness_margin и др.

```

Отдельно и независимо:

```
self_improve_code(target_id)              evolution.py
  ├─ propose_patch_llm                    кандидат от мозга с силой в programming
  ├─ evaluate_candidate                   песочница, по одному тесту
  ├─ decide                               строгое улучшение без регрессий
  └─ apply_patch                          бэкап + changelog + запись файла
```

## 4. Где находится истина

`mana/verifier.py` — единственный источник, не являющийся языковой моделью.

**Сильная сторона, которую нужно сохранить и развить.** В
`execution.py:261` уже есть градация доверия по признаку *кто автор оракула*:

```python
TRUST_INDEPENDENTLY_VERIFIED   # арифметика: оракул вычислен нами из текста задачи
TRUST_MODEL_TESTED             # тесты написаны той же моделью, что и ответ
TRUST_UNVERIFIED               # проверки не было
```

и `TRUST_QUALITY_CAP` ограничивает, сколько качества можно получить за каждый
уровень. Это ровно то различение, которое требуется для Self Model: свидетельство
градуируется по независимости источника, а не по факту «проверка прошла».
**Переиспользовать, не изобретать заново.**

**Слабые стороны — обе проверены экспериментально.**

`verifier.py:63` — `_safe_math_node` приводит всё к `float`:

```
999999999999999999 * 3  →  3e+18   (верно: 2999999999999999997),  ok: true
```

Источник истины уверенно выдаёт неверный ответ на целых числах.

`verifier.py:96` — политика песочницы построена как AST-денилист и обходится
индирекцией:

| код | вердикт политики |
|---|---|
| `print(eval('1+1'))` | заблокировано |
| `f = eval` затем `f('1+1')` | **пропущено** |
| `g = globals()`, `g['__'+'builtins'+'__']` | **пропущено** |

Для кода, который система генерирует сама и вписывает в собственные исходники,
это не граница безопасности.

## 5. Бенчмарк

`pipeline.py:357–390` — `BenchmarkSuite`, три набора:

| набор | задач | пример оценки |
|---|---|---|
| `train_tasks` | 7 | `["391"]`, `["верси"]`, `["тест"]` |
| `generalization_tasks` | 6 | `["323"]`, `["памят"]` |
| `holdout_tasks` | 8 | `["252"]`, `["измен"]`, `["нет"]` |

Оценка — **вхождение подстроки** в ответ. Всего **21 задача**.

Это весь сигнал качества MANA. Через него считается fitness, через него
принимаются мутации генома, и он же служит оракулом для патчинга кода.

## 6. Holdout

Отдельного holdout нет. `holdout_tasks()` лежит в том же файле, что и train,
и импортируется теми же вызовами.

**Отдельная проблема:** `_benchmark_holdout` — это **мутабельный флаг на самом
агенте** (`core.py:122`), который читают `confidence.py:134`, `confidence.py:153`
и `routing.py:162`, чтобы отключить обучение во время holdout-прогона.

Намерение верное: не учиться на holdout. Но реализация означает, что
**агент знает, когда его оценивают, и ведёт себя иначе**. Флаг живёт на
эволюционируемом объекте, а не за границей. Это первый кандидат в Immutable Core
и первый канал утечки, который нужно закрыть.

## 7. Что реально эволюционирует

Ровно две вещи.

**`PipelineSpec`** — 30 полей, изменяются GA-мутациями с группами
(`routing`, `compute`, `verification`, `graph`, `llm`, `brains`, `memory`, `web`).
Пространство: булевы флаги, числовые параметры, выбор из закрытых списков и
последовательность узлов графа из 8 разрешённых.

**Одна функция кода** — `ExecutionMixin._local_fallback`, единственная запись в
`code_evolution.WHITELIST`.

Всё. Больше ничего в системе не изменяется от опыта устойчиво.

## 8. Что ошибочно считается самообучением

Это самый важный раздел аудита.

### 8.1 «Обученный роутер» не учится на работе

`_record_learned_route_example` вызывается **из одного места** —
`benchmarking.py:127`, то есть только внутри routing-бенчмарка, с заранее
размеченным `expected`. Живые диалоги (`execution.py:493`, `routing.py:338`)
пишут только `_record_route_outcome` и в обучающую выборку не попадают.

Хуже: признаки в `_routing_feature_vector` (`routing.py:108`) — это выходы
`_task_category` и тех же keyword-правил, которые классификатор должен был бы
заменить. Логистическая регрессия дистиллирует правила в саму себя. Новой
информации не появляется.

### 8.2 UCB — не UCB

`experience.py:82`: `mean_quality + coef * sqrt(total/n)`, тогда как UCB1 —
`sqrt(2·ln(total)/n)`. Без логарифма член разведки растёт как √total: при
total = 10 000 и n = 100 он равен 3.5 против качества в диапазоне [0, 1]. Отбор
вырождается в «бери наименее опробованное» и не сходится никогда.

### 8.3 Кэш фитнеса сравнивает несравнимое

`benchmarking.py:324` — ключ кэша это `spec.key() | task_ids | seed | "v473"`.
В него не входят: включён ли LLM, какие мозги доступны, какая модель, доступен ли
веб, изменялся ли код. Прогнали цикл офлайн — потом включили мозги — GA возьмёт
из кэша число, измеренное в другой среде, и сравнит с ним нового чемпиона.
После `self_improve_code` весь кэш устарел, но используется.

### 8.4 Что действительно учится

`routing_stats` в `_record_route_outcome` и `ewma_quality` мозгов в
`record_outcome` — реальная обратная связь по исходам живой работы. Узко, но
честно. Это единственные два механизма, где опыт превращается в изменение
поведения без участия бенчмарка.

## 11. Что должно стать неизменяемым

Физическая граница — отдельный пакет `mana/core/`, недостижимый ни для
`code_evolution`, ни для генома:

- оракулы задач и вычисление правильного ответа;
- скрытый holdout и правило, что он не читается вне ворот;
- правила приёмки, регрессии и отката;
- границы песочницы и политика безопасности;
- бюджеты экспериментов и лимиты ресурсов;
- журнал аудита;
- определения успеха, новизны и переноса;
- **флаг режима оценки** — сейчас `_benchmark_holdout` на агенте.

`code_evolution._NEVER_PATCHABLE` уже существует и содержит 8 файлов. Расширить
до правила «всё в `mana/core/` непатчаемо» и проверять по каталогу, а не по
списку имён.

**Инвариант, который нужно закрепить тестом:** ни одна запись в `WHITELIST` не
может указывать на файл, содержащий оракул. Сейчас `pipeline.py` (где живёт
`BenchmarkSuite`) в `_NEVER_PATCHABLE` **не входит** — при расширении whitelist
агент сможет патчить собственный тестовый набор.

## 13. Архитектурные конфликты

Фиксирую явно, по §39, вместо обхода костылём.

### Конфликт А — оракул не выдерживает Level 2 и Level 3

21 задача с подстрочной оценкой не позволяет отличить новый когнитивный механизм
от шума. Открытие операторов и представлений требует сотен задач с однозначно
проверяемым ответом.

*Минимальный путь миграции:* генераторы задач в `mana/core/tasks/`, каждая задача
несёт вычислимый эталон и проверяется без языковой модели. Старый
`BenchmarkSuite` остаётся как один из наборов для обратной совместимости
существующих тестов, но перестаёт быть источником истины для приёмки.

### Конфликт Б — режим оценки живёт внутри оцениваемого

`_benchmark_holdout` — атрибут агента. Его читают три модуля, чтобы менять
поведение. Пока это так, «MANA не может улучшить себя, изменив механизм,
объявляющий её улучшенной» — декларация.

*Минимальный путь миграции:* режим переезжает в объект контекста оценки, который
создаёт Immutable Core и передаёт внутрь; агент его читает, но не владеет им.

### Конфликт В — программа плоская, а нужен граф

`graph_nodes` — кортеж строк с нормализацией «LLM обязателен, EVALUATE ровно один
и последний». Дедупликация в `_graph_for_task` схлопывает повторные проходы, то
есть цикл CRITIC→REPAIR→CRITIC невыразим.

*Минимальный путь миграции:* Cognitive IR как отдельное представление; `graph_nodes`
остаётся его частным случаем и компилируется в IR, пока новый исполнитель не
докажет паритет на существующих тестах.

### Конфликт Г — оракул самопатчинга совпадает с оракулом фитнеса

`_fallback_test_cases()` берёт train + generalization + **holdout** целиком.
Патч кода оптимизируется под те же строки, по которым потом измеряется пайплайн.

*Минимальный путь миграции:* оракул для `code_evolution` — отдельный набор,
физически недоступный из наборов приёмки пайплайна.

## 15. Что дальше

Порядок отличается от ТЗ в одном месте: **измерительный слой поднят на первую
фазу**. Причина в конфликте А — всё остальное оценивается через него, и строить
открытие операторов поверх 21 подстроки значит фитить шум без способа это
заметить.

**Фаза 1 — Измерение и Immutable Core:**

1. `mana/core/` как физическая граница, правило непатчаемости по каталогу;
2. генераторы задач с вычислимым эталоном, 4 домена, сотни задач;
3. разделение TRAIN / DEV / HIDDEN HOLDOUT / TRANSFER;
4. режим оценки за границей, а не на агенте;
5. точная арифметика в верификаторе;
6. тест-инвариант: whitelist патчинга не пересекается с оракулами.

Только после этого имеет смысл геном, IR и операторы.

## 16. Близкие работы

По §31 — без заявлений о новизне. Идеи, которые MANA объединяет, существуют по
отдельности:

- открытый поиск и давление новизны — Novelty Search, MAP-Elites, POET;
- самогенерируемая программа обучения — Automatic Curriculum Learning;
- синтез программ мышления из операторов — DreamCoder и родственные подходы к
  library learning;
- самоулучшающиеся агенты с воротами приёмки — линия Voyager, ADAS, Gödel-machine-подобные
  конструкции;
- градация доверия к свидетельству — стандартная практика в экспериментальной науке.

Чего в этих работах обычно нет и что MANA пытается сделать иначе: **связать
