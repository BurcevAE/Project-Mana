# MANA 5.8.0

Версия продукта объявлена ровно в одном месте — `mana/version.py`. Каждая
подсистема версионируется отдельно и стартует с `1.0` в этом релизе.

```bash
python mana_run.py --version     # продукт + версии всех 24 подсистем
```

Правила повышения версии подсистемы:
`1.0 -> 1.0.1` — багфикс без смены поведения; `1.0 -> 1.1` — новое
поведение, совместимое; `1.0 -> 2.0` — вызывающий код надо менять.

**Версии обновляются вместе с изменением, а не потом.** Это проверяется:
`test_product_version_is_declared_once` падает, если продуктовая версия
изменилась без обновления теста, а `test_modules_changed_in_this_release_were_bumped`
следит за подсистемами, которые менялись. В 5.7.9 подняты `knowledge 1.1`, `agent_parts.context 1.1`, `config 1.1`;
добавлен `intent 1.0`. В 5.7.10 — `agent_parts.context 1.2`
(ворота коррекции распространены на веб; запрет утечки служебных меток
в ответ; правило про дату сниппета).

До этого релиза номер был захардкожен в пяти местах и успел разъехаться
на три разных значения одновременно (`5.4.0`, `5.4`, `5.3.1`).
`tests/test_versioning.py` падает, если литерал версии появится снова.


Это тот же код, что был в `MANA_5_4.py` (4683 строки), разложенный по модулям
без изменения поведения (плюс один найденный по пути баг — см. ниже).
Запуск и все CLI-флаги идентичны оригиналу.

### Как разбит `ManaAgent`

`ManaAgent` был единственным классом на 2489 строк / 100 членов (методы +
`VERSION`). Он разложен на 8 mixin-классов по зонам ответственности, и
`ManaAgent` теперь просто:

```python
class ManaAgent(CoreMixin, ContextMixin, RoutingMixin, ConfidenceMixin,
                 ExecutionMixin, BenchmarkingMixin, EvolutionMixin,
                 KnowledgeOpsMixin):
    pass
```

Это **не** переход на композицию (`self.router.classify(...)`) — миксины
специально выбраны вместо неё, потому что оригинальный класс имеет очень
плотные перекрёстные вызовы между "зонами" (эволюция вызывает бенчмаркинг,
исполнение вызывает роутинг и confidence, и т.д.), и вместо `self.foo` они
через weeks-old код опирались на общий `self`. Механический переход на
композицию потребовал бы переписать сотни вызовов и де-факто заново
протестировать всю систему без гарантии сохранения поведения. Mixin-подход
даёт ту же физическую модульность (каждый файл — своя зона, читается и
редактируется отдельно) при **нулевом изменении runtime-поведения**: все
миксины делят один и тот же `self`, поэтому перекрёстные вызовы работают
как раньше.

Проверено построчно и автоматически:
- Множество из 100 членов класса до/после разбиения совпадает **ровно**
  (`orig == new`, без пропусков и дублей).
- Тело каждого метода сверено **побайтово** с оригиналом; единственное
  отличие — одна намеренная правка (`ManaAgent._json_safe` →
  `CoreMixin._json_safe`, т.к. рекурсивный вызов статического метода
  теперь ссылается на класс в том же файле).
- Все прежние smoke-тесты (`--verify`, `--memory-status`,
  `--knowledge-status`, `--run-code`, offline `--self-improve`) дают
  идентичный вывод до и после разбиения.

Самый крупный оставшийся файл — `agent_parts/evolution.py` (871 строка:
`evaluate_pipeline`, причинный GA-цикл `evolve_pipeline`, `self_improve`).
Он всё ещё цельный, но это уже совсем другой масштаб задачи, чем
2489-строчный бог-класс — при желании его можно дальше разбить на
`evolution/search.py` (GA-цикл) и `evolution/acceptance.py`
(precheck/statistical/causal gates), но это не обязательно для того, чтобы
модифицировать что-то одно, не боясь задеть остальное.

Зависимости между модулями строго однонаправленные (снизу вверх по списку
выше) — `pipeline.py` не знает о `memory.py`, `memory.py` не знает об
`agent.py` и т.д. Это и есть тот "фундамент для роста": любой из нижних
слоёв (memory, llm, web, verifier) можно теперь тестировать, менять и
расширять изолированно, не трогая 2500-строчный `agent.py`.

## Найденный и исправленный баг

В оригинале опциональный импорт `sounddevice` был обёрнут в
`except ImportError:`. На машине без системной библиотеки PortAudio
`sounddevice` кидает не `ImportError`, а `OSError` — и **весь скрипт падал
при импорте**, даже с `--no-voice`. Это реально произошло в песочнице при
тестировании. Исправлено в `mana/optional_deps.py`: везде `except
Exception:` (как уже было для `fitz`). Стоит убедиться, что это исправление
попадёт и в любую копию, которую вы держите отдельно от этого проекта.

## Расширение пространства эволюции (graph_nodes)

Раньше `graph_nodes` (вычислительный граф пайплайна: какие узлы — `MEMORY`,
`WEB`, `LLM`, `CRITIC`, `REPAIR`, `SYNTHESIS`, `EVALUATE`, `EXECUTE` —
выполняются и в каком порядке) эволюционировал только выбором из **7
захардкоженных кортежей**. Теперь:

- `PipelineFactory.random_graph()` генерирует граф структурно: узлы
  `MEMORY`/`WEB` осмысленны только *до* первого `LLM` (материализуют
  контекст для него), узлы `CRITIC`/`REPAIR`/`SYNTHESIS`/`EXECUTE` — только
  *после* (работают с уже готовым черновиком). Каждый опциональный узел
  включается независимо с вероятностью `cfg.graph_mutation_rate` — поле,
  которое в оригинале было объявлено в `Config`, но нигде не читалось.
  Это даёт ~130+ различимых графов на 500 случайных генераций (против 7
  раньше) при теоретическом потолке порядка 300+ валидных
  структур — и подтверждено property-based тестом.
- Мутация `graph_nodes` раньше была одной операцией "выбери один из 7
  кортежей". Теперь это три точечных, причинно-локальных мутации
  (`graph_add_node`, `graph_remove_node`, `graph_reorder`), каждая меняет
  ровно один аспект графа — это соответствует философии "одна мутация →
  один измеримый эффект", на которой построен весь `evolve_pipeline`, но
  раньше не применялось внутри самого графового поля.

Заодно нашёл и исправил два бага в `PipelineSpec.normalize()`:
1. `"EXECUTE"` отсутствовал в `allowed_nodes` — любой геном с этим узлом
   (реально поддерживаемым исполнителем в `ExecutionMixin`) молча
   лишался его при нормализации, то есть **эволюция физически не могла
   выбрать верификацию кода через `EXECUTE`**.
2. `EVALUATE` добавлялся в конец, только если отсутствовал вовсе — если
   он оказывался не на последнем месте (или обрезался финальным
   `nodes[:10]`), исполнитель прерывал adaptive-цикл сразу же (`current`
   ещё `None`) и полностью проваливался в обычный одиночный вызов LLM,
   то есть остаток эволюционировавшего графа никогда не исполнялся.
   Теперь `EVALUATE` гарантированно ровно один и всегда последний.

Проверено:
- Property-based тест (`PipelineFactory.random/mutate/crossover`, 500+200
  прогонов + 3 сконструированных вручную вырожденных случая) — каждый
  сгенерированный геном валиден: `LLM` присутствует, `EVALUATE` ровно один
  и последний, без дублей узлов, длина ≤ `graph_max_nodes`.
- Stress-тест: 50 сидов × 200 последовательных мутаций = 10 000 шагов
  подряд без единой невалидной генерации.
- Полный offline `--self-improve 2 --generations 2 --population 4` (2
  цикла эволюции, графовые мутации внутри реального GA-цикла) — без
  исключений, идентично прежнему поведению по остальным метрикам.

## Фаза 1 запроса «улучшайся и подстраивайся под машину»: hardware-adaptation + Tool-реестр

Из большого запроса (адаптация под машину, self-code-improvement, слоистая
графовая память, обучение из интернета, само-встраивание инструментов,
голос) в этом шаге реализованы две фундаментальные, низкорисковые части —
остальное описано ниже как согласованный план, а не сделано вслепую (см.
"Позиция по самым рискованным пунктам").

### `mana/hardware.py` — адаптация под текущую машину

`detect_hardware()` определяет CPU-ядра, RAM (`psutil`, если установлен,
иначе `/proc/meminfo`, иначе — молчаливый fallback без изменений), и
CUDA-доступность (через уже существующий `optional_deps.torch`), и относит
машину к `tier`: `low`/`medium`/`high`.

`apply_hardware_profile(cfg, profile)` **сужает** уже заданные значения
`Config` (никогда не увеличивает то, что человек явно выставил через CLI —
`evolution_workers` из `--evolution-workers` остаётся потолком, hardware
может его только уменьшить):
- `evolution_workers` ≤ `cpu_count - 1` (оставляет ядро локальному LLM-бэкенду);
- на `low`: меньше `strategy_population`/`strategy_generations`/бюджета
  оценок за цикл, больше таймауты LLM (медленнее инференс), `use_embeddings
  = False` (самая тяжёлая опциональная зависимость — sentence-transformers
  — не грузится, `KnowledgeBase` уже использует TF-IDF fallback);
- на `high`: чуть более строгий таймаут LLM (не ждать зависший вызов так
  долго, как на слабой машине).

Вызывается один раз в `CoreMixin.__init__`, **до** того, как остальной
код читает эти поля Config; что изменилось — не скрыто: печатается в
баннере запуска и доступно через `agent.hardware_status()` /
`--hardware-status`. Отключается через `Config.hardware_auto_adapt=False`
или `--no-hardware-adapt`.

Проверено на самой песочнице (1 CPU / 3.9GB — тут же классифицируется как
`low`, все 7 полей сужены корректно, полный offline `--self-improve` цикл
после адаптации отрабатывает идентично).

### `mana/tools.py` — единый Tool-реестр

`BaseTool`/`FunctionTool`/`ToolRegistry` — минимальный протокол вместо
того, чтобы `WebSearcher`/`LocalVerifier` вызывались напрямую по имени из
глубины `ExecutionMixin`. `build_default_registry(agent)` оборачивает уже
существующие возможности в инструменты: `web_search`, `verify_arithmetic`,
`run_code`, `search_knowledge_base`, `search_conversation_memory`.
Живёт на `agent.tools`, видно через `--list-tools` / `agent.tools_status()`.

Это **основа** для "агент сам находит и встраивает нужные инструменты" —
`ToolRegistry.register()` уже даёт место, куда новый инструмент встаёт, но
сам этот шаг сейчас не реализует автономную генерацию кода нового
инструмента (см. ниже почему).

Внутренние вызовы (`ExecutionMixin`/`RoutingMixin`) в этом шаге **не**
переведены на вызов через реестр — они по-прежнему обращаются к
`self.web`/`self.verifier` напрямую, чтобы не трогать уже протестированный
граф исполнения без необходимости. Реестр параллельно живёт как
инспектируемый источник правды "что агент умеет"; переключение
исполнителя графа на реестр — небольшая последующая правка, не
architecture-level риск.

## Позиция по самым рискованным пунктам запроса

Часть запроса — «улучшить собственный код и алгоритмы» и «сам себя
встраивать новые инструменты» — по сути один и тот же класс задачи:
**агент, изменяющий свои собственные возможности без надзора.** Это не
формальность, а инженерный риск: неаккуратный self-patch может тихо
сломать агента или (если ослабить проверки) исполнить произвольный код.
У самого проекта уже есть подходящая дисциплина для этого — весь
`evolve_pipeline` устроен как: предложить кандидата → прогнать в
изолированной среде на benchmark/holdout → статистический precheck →
принять только при строгом улучшении → возможность отката. План — сделать
для изменений *кода* и *новых инструментов* ровно то же самое, а не
обойти эту дисциплину:

- **Self-code-improvement**: агент предлагает патч конкретной, заранее
  разрешённой функции/модуля → патч гоняется в sandbox (уже есть —
  `LocalVerifier`) против полного regression+benchmark набора → принимается
  только при строгом улучшении фитнеса, с версионированием и откатом.
  Никакого "тихого" самопереписывания без диффа, без прогона тестов и без
  возможности откатить.
- **Автономное встраивание новых инструментов**: агент может *предложить*
  новый инструмент (обёртку над новым API/библиотекой), но подключение
  новой сетевой/исполняемой возможности проходит через тот же gate, что и
  self-code-improvement выше — не полностью автономно и незаметно.

Это не искусственное ограничение "потому что ИИ" — тот же принцип уже
применяется в проекте к обычному тюнингу `PipelineSpec` (строгий
before/after, holdout, откат). Расширяю его на код и инструменты, а не
исключаю для них.

## Фаза 2: gated self-improvement pipeline (код) + графовая память

Реализовано в этом шаге — оба пункта из плана выше, теперь работающие,
подключённые и протестированные, а не только описанные.

### `mana/code_evolution.py` — gated self-improvement кода

Зеркалит дисциплину `evolve_pipeline`: предложить патч → прогнать в
существующей sandbox (`LocalVerifier`, тот же `--enable-local-exec`, что и
`--run-code`) → строгий gate → применить с бэкапом/changelog либо
отклонить. Жёсткие границы: whitelist патчуемых целей — константа в коде,
агент не может расширить её сам; кандидат — чистая функция без `self` и
side-effects, проходит статическую AST-проверку и уже существующий
import/call blocklist `LocalVerifier._static_policy` до всякого запуска;
принимается только при **строгом** улучшении без единой регрессии
(ничья — это отказ, как и в `_strict_acceptance`); каждое применение —
это сначала бэкап и запись в `mana_code_history/changelog.jsonl`, потом
патч, с `agent.rollback_code()` для отката.

Whitelist сейчас — 2 чистые функции: `_local_fallback` (fallback без LLM)
и `_task_category` (классификатор задач); тестовый оракул — сам
`BenchmarkSuite`, ничего нового не придумывал.

**Реальный результат, не синтетика**: эмпирически прогнал `_local_fallback`
против всех 21 задачи бенчмарка с must_contain — 3 проваливались
(падежные несовпадения в регэкспах, например паттерн ждал "историю
изменений", а реальный текст задачи — "история изменений"). Написал
патч, прогнал через весь pipeline: gate принял (18/21 → 21/21 прохождения),
применил через `agent.self_improve_code()`. Диф и бэкап лежат в
`mana_code_history/`.

Попутно поймал и исправил 2 бага **в собственном новом коде** уже во
время тестирования (не в существующем MANA): конфликт кавычек в
генераторе assert-сообщений ломал sandbox-скрипт на кандидатах, для
которых baseline уже не проходил все тесты; `ast.FunctionDef.lineno`
указывает на строку `def`, а не декоратора, из-за чего `@staticmethod`
задваивался при применении патча. Оба пойманы именно потому, что гонял
пайплайн на реальных, а не тривиальных кейсах, и переприменял патч после
исправления, чтобы в поставке остался только один чистый вызов.

CLI: `--list-code-targets`, `--self-improve-code TARGET_ID
--code-instruction "..."` (без LLM нужно передавать кандидат напрямую
через `agent.self_improve_code(..., candidate_source=...)` — CLI-путь
требует включённого `--no-llm`≠true и `--enable-local-exec`),
`--code-history [TARGET_ID]`, `--rollback-code TARGET_ID`.

### `mana/graph_memory.py` — слоистая графовая память

Надстройка над существующим `MemoryManager` (переиспользует его SQLite-
соединение, эмбеддер и `semantic_search`, не заводит вторую БД):

- **Дистилляция вместо сырого текста.** `distill_turn()` — LLM-путь (одно
  предложение-вывод) или эвристический fallback без LLM: обрезка
  "воды"-филлеров (регэкспы на русские/английские слова-паразиты:
  "короче", "в общем-то", "как бы", "well", "you know"...) + отбор
  самых информативных предложений (эвристика по цифрам/заглавным
  токенам/длине) с жёстким лимитом символов. `events`-таблица по-прежнему
  хранит сырой диалог для краткосрочной непрерывности — граф не заменяет
  её, а добавляет сжатый долгосрочный слой поверх.
- **Реальный граф, не таблица.** Новая таблица `memory_edges` поверх уже
  существующих `memory_items`-узлов (переиспользованы как graph-узлы через
  новый `item_type`): рёбра `FOLLOWS` (временная цепочка в сессии),
  `MENTIONS` (реплика → сущность), `PART_OF` (реплика → эпизод-rollup).
- **Два слоя.** Слой 1 — дистиллированная реплика на каждый обмен. Слой 2
  — `maybe_rollup_episode()` каждые `memory_auto_compress_after` реплик
  сжимает недавние узлы слоя 1 в один узел-эпизод (сжатие сжатого),
  связывая их `PART_OF`.
- **Контекст через обход графа, не просто top-k.** `graph_context()`
  берёт небольшой набор seed-узлов через `semantic_search`, затем обходит
  рёбра на `depth` шагов с затуханием веса за хоп, добавляет короткий
  "recency"-хвост, ранжирует и обрезает по бюджету символов.

**Строго проверено, не на словах**: собрал синтетический граф, где реплика
про "Git" встречается дважды с совершенно разной формулировкой (разделена
5 нерелевантными "шумовыми" репликами). Прямой семантический поиск
(`semantic_search`, ограниченный 2 seed'ами) **не находит** первую
реплику про Git при запросе про вторую — подтверждено явной проверкой
`assert n_git not in trace["seeds"]`. Обход графа на 2 хопа через общую
сущность `git` **находит** её и включает в финальный ранжированный
контекст — `assert n_git in trace["used"]`. По пути нашёл реальную проблему
дизайна: количество seed'ов масштабировалось вместе с итоговым лимитом
результатов, из-за чего при большом лимите слабые прямые совпадения
"забивали" находки через граф — исправил, разделив `seed_limit` и `limit`
на независимые параметры.

Подключено в `solve_task()`: каждый настоящий пользовательский обмен
пишется в граф через `record_turn()` + периодический
`maybe_rollup_episode()`; синтетические запросы бенчмарка/эволюции (они
идут через `answer(save_memory=False)` напрямую, минуя `solve_task`)
**не** попадают в граф — проверено. CLI: `--graph-memory-status`,
`--graph-memory-search QUERY`.

**Обновление**: чтение теперь тоже подключено — см. раздел "Фаза 3" ниже,
пункт 1 из старого плана закрыт.

## Фаза 3: чтение графа памяти вплетено в реальный ответ

`_build_context` (`ContextMixin`, единственное место, которое реально
формирует промпт для LLM в `_answer_core`) теперь дополнительно вызывает
`graph_memory.graph_context()` и добавляет отдельный размеченный блок
`[GRAPH MEMORY]` — рядом с уже существующими `[RECENT CONVERSATION]`,
`[VERIFIED EVIDENCE]` и т.д., а не смешивая с ними, чтобы происхождение
(обход графа vs. прямой семантический/фактовый поиск) оставалось видно и
LLM, и в `trace["graph_memory"]`.

Новые поля `Config`: `graph_memory_context_enabled` (вкл/выкл),
`graph_memory_depth`, `graph_memory_seed_limit`, `graph_memory_limit`,
`graph_memory_char_budget`, `graph_memory_episode_every_n_turns`.

Ошибка чтения графа не может сломать ответ — обёрнуто в try/except с тем
же контрактом graceful degradation, что и остальные источники контекста
в этом методе (evidence/legacy-память/web).

**Проверено на реальном пути `_build_context()`**, не отдельным API:
записал через `graph_memory.record_turn()` явный обмен про Git, затем 4
не связанных по теме реплики, затем вызвал `agent._build_context(...)`
для **иначе сформулированного** вопроса про ветки в Git — блок
`[GRAPH MEMORY]` в реальном сгенерированном контексте содержит исходную
реплику про Git, найденную через обход графа, а не прямым совпадением
текста. Плюс полная регрессия: `--verify`, `--graph-memory-status/search`,
`--routing-benchmark`, offline `--self-improve` (2 поколения, 3 кандидата)
— всё воспроизводимо, ничего не сломано.

Отдельно проверил и задокументировал ограничение: с выключенным LLM
(`--no-llm`) `_local_fallback` часто возвращает **одинаковый** общий текст
для разных вопросов ("Недостаточно данных..."), из-за чего в офлайн-режиме
многие узлы графа неотличимы по содержанию друг от друга — это ограничение
самого fallback-словаря (уже описано выше), а не графовой памяти: с
включённым LLM каждая реплика содержательно уникальна, и обход графа
работает так, как показано в основном тесте.

## Фаза 4: Tool Engine — реестр стал реальным путём исполнения, не декорацией

Раньше `ToolRegistry` существовал, но `ExecutionMixin`/`ContextMixin`/
`ConfidenceMixin` по-прежнему вызывали `self.llm`/`self.web`/`self.verifier`/
`self.memory` напрямую — реестр был инспектируемым списком сбоку, а не
реальным путём диспетчеризации. Это переделано целиком, одним
согласованным проходом по всей кодовой базе, а не по одному узлу графа за
раз.

### Архитектурная граница (осознанная, задокументирована в `tools.py`)

Инструментом становится то, что агент **условно выбирает** вызвать исходя
из задачи или `PipelineSpec` (web-поиск, локальное исполнение кода, какой
LLM-провайдер, консультироваться ли с графовой/плоской памятью). То, что
выполняется **безусловно** как служебная бухгалтерия — запись в event-лог
(`persistent_memory.remember_*`), внутренняя оркестрация
`MemoryManager.context_for` (сам вызывает `semantic_search` у себя же),
статическая проверка безопасности LLM-сгенерированного кода перед
исполнением (`LocalVerifier._static_policy`) — остаётся прямым вызовом.
Реестр опосредует **межсубсистемные** решения агента на уровне оркестрации
(`agent_parts/*`), а не каждый внутренний вызов внутри одной подсистемы
(`memory.py`/`verifier.py`/`llm.py` по-прежнему вызывают свои методы
напрямую). Смешать эти два уровня значило бы превратить реестр в декорацию
вокруг вызовов, которые никогда не были опциональными — то есть вернуться
к тому же самому недостатку, который и предстояло исправить.

### Новые инструменты (было 5, стало 9)

`llm_generate` (самое важное — единая точка входа для **всех** вызовов
LLM в агенте: ответ, критик, repair, synthesis, генерация bundle для
верификации кода, дистилляция графовой памяти), `verify_answer` (отдельно
от `verify_arithmetic` — проверка соответствия ответа факту, извлечённому
из задачи), `search_graph_memory`, `write_memory`. У каждого инструмента
теперь есть метаданные `requires_network`/`requires_exec`/`requires_llm`/
`cost_hint` и метод `is_available()` — задел под будущий Planner (честно
помечен как качественная, не калиброванная оценка, не измеренная).

### Что реально мигрировано на `self.tools.call(...)`

- `context.py`: `_build_context` целиком — граф-память, `KnowledgeBase`,
  web-поиск (с поправкой на dict-контракт вместо object-атрибутов, раз
  `search_knowledge_base` возвращает `KnowledgeEntry.to_dict()`).
- `execution.py`: `_critic`, `_generate_verification_bundle`,
  `_autonomous_execute`, `_graph_for_task`, REPAIR/SYNTHESIS-ветки
  adaptive-графа, оба вызова LLM в `_answer_core`, обе записи в память.
- `confidence.py`: все проверки `use_critic` в `_architecture_spec`,
  VOC-оценка, `_verification_policy`.
- `core.py`: баннер статуса, чтение/запись графовой памяти, новый
  choke-point `_llm_call`/`_verify_answer`/`_tool_available`.
- `evolution.py`: `self_improve_code` — `code_evolution.propose_patch_llm`
  переведён с приёма сырого `LLMClient` на приём `_llm_call`-совместимого
  callable (сигнатура `(prompt, *, temperature, context_tag) -> (text,
  meta)`), чтобы модуль не импортировал `agent_parts` и оставался
  развязанным, но при этом шёл через тот же choke-point.
- `knowledge_ops.py`: `acquire_topic_from_web`.
- `cli.py`: `--verify`, `--run-code`; интерактивный REPL: `/verify`.

**Проверено полным прогоном после миграции**, не только компиляцией:
- `--verify`, `--run-code` (через `agent.tools.call` теперь) — идентичный вывод.
- Полный диалог через `solve_task()` офлайн: fallback-ответы, запись в
  `KnowledgeBase` через `write_memory`, запись/чтение графовой памяти —
  `[GRAPH MEMORY]` и `[MEMORY]` блоки оба на месте в реальном `_build_context`.
- Полный adaptive-compute цикл (`route_mode="auto"`) на задаче "17*23":
  граф `LLM→EXECUTE→EVALUATE`, `EXECUTE` реально вызвал `verify_answer`
  инструмент, `verification_kind: "arithmetic"`, `verification_used: true`
  — подтверждает, что миграция `_autonomous_execute` работает в реальном
  цикле, не только изолированно.
- `--self-improve` (offline, 2 поколения) и `--routing-benchmark` —
  идентичное поведение до/после.
- `self_improve_code()` (gated code-evolution из Фазы 2) — проверил оба
  пути: ручной кандидат и graceful-отказ при выключенном LLM
  (`{"ok": false, "reason": "no candidate_source given and LLM is disabled"}`,
  без падения). Заодно ручной тест самого пайплайна нашёл и применил
  **настоящее** улучшение: `_task_category` получил ветку `"logic"` для
  задач сравнения (0.9 vs 0.89 и т.п.), пройденных тестов стало 15/21
  вместо 13/21 — раньше эта категория не производилась классификатором
  вовсе (см. "Область для улучшения" из предыдущего анализа возможностей).

### Не тронуто сознательно (интра-субсистемные вызовы)

`LocalVerifier._static_policy` (внутренняя проверка безопасности перед
исполнением LLM-сгенерированного кода), `MemoryManager.context_for`'s
внутренний `semantic_search`, `graph_memory.record_turn`/
`maybe_rollup_episode`/`stats` при обычной работе `solve_task` (безусловная
бухгалтерия, не выбор) — остаются прямыми вызовами по границе, описанной
выше. `code_evolution.evaluate_candidate` по-прежнему получает
`self.verifier` напрямую для sandbox-тестирования кандидатов — это
внутренняя инфраструктура самого gated-pipeline, не решение агента по
ходу ответа на задачу.


## План на дальнейшие шаги (не реализовано)

1. **Planner поверх Tool Engine.** Метаданные (`cost_hint`, `requires_*`,
   `is_available()`) теперь есть у каждого инструмента, но ничего пока не
   выбирает между ними по стоимости/выгоде -- граф вычислений всё ещё
   выбирается эволюционировавшим геномом или хардкод-эвристикой в
   `_select_architecture`, просто теперь *исполняет* узлы через
   инструменты, а не по имени. Следующий шаг -- реально использовать эти
   метаданные для выбора, не только для отображения через `--list-tools`.
2. **Автономный tool-discovery**: агент ищет в интернете "есть ли
   библиотека/API для X", предлагает интеграцию через `code_evolution`
   (новый инструмент -- это код, тот же gate), а не пишет и подключает код
   в обход него. Теперь, когда `ToolRegistry` -- реальный путь исполнения,
   а не декорация, "добавить инструмент" осмысленно означает "добавить
   запись в реестр", а не переписывать `ExecutionMixin`.
3. **Голос** -- база уже есть (`VoiceInterface`: wake-word, VAD, Whisper
   STT, Silero/pyttsx3 TTS); "естественность" -- вопрос качества/тюнинга
   промптов синтеза речи, не структурный пробел. Ни разу не тестировал
   лично в этом диалоге (нет микрофона/аудио в песочнице).
4. **Расширить whitelist `code_evolution`** на более значимые цели по мере
   того, как первые две (`_local_fallback`, `_task_category`) докажут себя
   на практике -- сознательно начал с малого и безопасного, не с самого
   ценного.
5. **Качество эвристического дистиллятора без LLM** (графовая память) --
   регэксп-фильтрация "воды" работает и протестирована, но заведомо
   грубее, чем LLM-путь; стоит инвестировать только если агент часто
   будет работать без LLM.
6. **Memory Engine 2.0** (миграции схемы, инкрементальный FTS вместо
   полного rebuild при каждом старте, реальный vector index вместо
   линейного скана по `memory_items`) -- реальный технический долг,
   подтверждённый чтением кода, но не блокирует ничего при текущем
   масштабе (десятки узлов, не миллионы) -- сознательно не первый
   приоритет.
